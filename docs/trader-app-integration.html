01 Integration model

It's a WebView — not native screens or direct API calls.

Deal Flow is a self-contained web app served through the gateway at a single base path. You embed the URL in a WebView; the page makes its own API calls. You do not build native screens or call the /api/* endpoints directly — they're documented in §5 for reference and debugging only.

The one thing to get right

Open https://api.bijnis.com/g/deal-flow in the WebView. The initial page load is public (no auth). The page then calls /api/*, which require the FOS headers in §4 — and the page attaches none itself, so the app must inject them.

02 Feature flag (backend-controlled)

The server decides who gets it — no app release to change the audience.

There are two independent controls; keep them separate:

ControlScopeOwned byUse
DEAL_FLOW_URL (gateway config)Whole feature, everyoneOps / platformGlobal master switch / kill-switch. Unset → /g/deal-flow 404 for all.
dealFlow.enabled (backend flag)Per user / cohortBackend, read by appThe rollout knob. Decides who sees the entry, changeable live.

For rolling out "to any users", use the backend flag: the app reads a per-user value on login and shows the Deal Flow entry only when it's on. Because the server owns the value, you can flip the audience anytime without an app build.

// returned per authenticated trader by the app's config endpoint
{
  "dealFlow": {
    "enabled": true,                                  // server decides per user
    "url": "https://api.bijnis.com/g/deal-flow"       // lets you re-point without an app build
  }
}

The server computes enabled from a targeting rule you control centrally — any of:

  • All traders (full launch),
  • Percentage rollout (hash of fosId → bucket, e.g. 10% → 50% → 100%),
  • Cohort / allowlist — specific fosIds, sellerIds, regions, or reporting hierarchy.
Frontend dev's call — mechanism

Where the flag lives (remote config, the app's existing per-user config/bootstrap API, or a feature-flag service) is up to the app team. The contract only needs: a boolean the app reads per user, and the entry rendered when it's true. The url field is optional but recommended.

Optional hardening: the flag above controls visibility. If you want it enforced (a non-enabled user who reaches the URL gets no data), the platform team can add a server-side allowlist check in the gateway keyed by sellerId/fosId — recommended once you go past a trusted pilot.

// Opens the embedded web UI with FOS auth headers injected (see §4)
function openDealFlow(url) {
  navigation.navigate('DealFlowWebView', { uri: url });
}

Inside the WebView

The trader enters a retailer phone number (the retailer's registered companyPhone). The page loads that retailer's on-stock cart for this trader's seller, shows per-item pricing / margin / discount and a live deal summary, plus a "Discount Eligible SKUs" sheet. Everything is seller-scoped by the token — a trader only ever sees their own seller's carts.

04 Auth & header injection

Inject the FOS headers into every /g/deal-flow/* request.

The deal_flow page's own fetch() calls carry no auth. In the app you must inject the FOS auth + context headers into all WebView requests to /g/deal-flow/*. react-native-webview's source.headers only applies to the top-level navigation, not sub-requests — so patch fetch / XMLHttpRequest via injectedJavaScriptBeforeContentLoaded.

This is the same header set the app already sends to other gateway APIs (e.g. /g/psfa/*):

HeaderValueNotes
tokenFOS JWTprimary auth token
AuthorizationFOS JWTsame token (gateway reads either)
sessiontokenFOS JWTsame token
User-Typefosrequired — userservice fos-restriction
Platformreact-android / react-iosrequired
App-Versione.g. 3.1.7required
Build-Versione.g. 202required
Package-Namecom.bizcrum.rm.apprequired
Device-Iddevice idrequired
Android-Sdk-Versione.g. 31required
Do not send these

Seller-Id, Fos-Id, Auth-Key — the gateway derives and injects them from the validated token and strips any client-supplied copies (anti-spoofing). The trader's sellerId comes from the token; the app does nothing for it.

RN WebView injection

const AUTH_HEADERS = {
  token: FOS_JWT,
  Authorization: FOS_JWT,
  sessiontoken: FOS_JWT,
  'User-Type': 'fos',
  Platform: 'react-android',
  'App-Version': appVersion,
  'Build-Version': buildVersion,
  'Package-Name': 'com.bizcrum.rm.app',
  'Device-Id': deviceId,
  'Android-Sdk-Version': sdkVersion,
};

const injected = `
(function () {
  var H = ${JSON.stringify(AUTH_HEADERS)};
  var of = window.fetch;
  window.fetch = function (input, init) {
    init = init || {};
    var url = typeof input === 'string' ? input : (input && input.url) || '';
    if (url.indexOf('/g/deal-flow/api/') !== -1) {
      init.headers = Object.assign({}, init.headers || {}, H);
    }
    return of(input, init);
  };
  var oo = XMLHttpRequest.prototype.open, os = XMLHttpRequest.prototype.send;
  XMLHttpRequest.prototype.open = function (m, u) {
    this.__df = (u || '').indexOf('/g/deal-flow/api/') !== -1;
    return oo.apply(this, arguments);
  };
  XMLHttpRequest.prototype.send = function () {
    if (this.__df) { for (var k in H) this.setRequestHeader(k, H[k]); }
    return os.apply(this, arguments);
  };
  true;
})();
`;

<WebView
  source={{ uri: dealFlow.url }}
  injectedJavaScriptBeforeContentLoaded={injected}
  sharedCookiesEnabled={false}
/>
Token refresh

If the JWT can expire mid-session, re-inject the current token (the app already manages FOS token lifetime for other webviews). A stale token surfaces as 401 on the /api/* calls — the UI then shows "Failed to load cart".

05 API reference

What the WebView calls — for reference & debugging.

Base https://api.bijnis.com/g/deal-flow. All /api/* except /api/health require the §4 headers. Auth failures return 401 {"status":401,"message":"Unauthorized"}.

GET /api/health

Public liveness. 200 when up. No auth.

GET /api/cart?phone=<companyPhone>

The retailer's deal cart, scoped to the trader's seller (from token).

  • phone (required) — retailer's companyPhone.
  • 200 → CartResponse (§6). items: [] with 200 means the retailer has no on-stock cart under this seller — not an error.
  • 400 phone is required / seller context missing (the latter only if the gateway didn't inject Seller-Id — shouldn't happen in the app).
  • 500 Failed to fetch cart.
POST /api/cart

Recalculate the deal after the trader edits quantities / applies discounts.

{
  "phone": "9876543210",
  "quantities": [ { "variantid": 123, "sizeid": 45, "setCount": 2 } ],
  "discounts":  [ { "variantid": 123, "sizeid": 45, "amount": 10 } ]
}
  • quantities, discounts optional. In a discount, use amount or pct.
  • 200 → CartResponse (recomputed).
GET /api/discount-eligible-skus?pincode=<pincode>

SKUs eligible for discount for a pincode (the UI passes the cart's pincode).

  • pincode (required).
  • 200 → { "pincode": string, "items": DiscountEligibleSku[] }.
  • 400 pincode is required.

07 Rollout & rollback

The backend flag is the day-to-day control.

  • Rollout — ship the flagged entry once; then widen dealFlow.enabled server-side (pilot cohort → percentage → all). No further app releases.
  • App-side rollback — set dealFlow.enabled = false for the affected users. Instant, no build.
  • Backend rollback (ops) — unset DEAL_FLOW_URL on the gateway → /g/deal-flow returns 404 fleet-wide. The global kill-switch, independent of the per-user flag.

08 Security notes

Pricing and margins are exposed only behind FOS auth.

  • Every /api/* except health is validated against userservice with a fos restriction, and the seller is bound to the token. Do not add any path that bypasses this.
  • Never inject Seller-Id / Fos-Id / Auth-Key from the client — the gateway owns them.
  • Pricing, margin and discount data must never render outside an authenticated FOS session.
  • The per-user flag controls visibility; for hard access control, pair it with a server-side allowlist in the gateway (see §2).
